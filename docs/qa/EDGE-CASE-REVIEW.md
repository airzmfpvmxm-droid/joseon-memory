# 독립 경계 조건 검토

검토일: 2026-11-20. 대상: `js/app.js`, `js/games/grain.js`, `rhythm.js`, `puzzles.js`, `action.js`의 현재 소스. 과거 검토 문서는 근거로 사용하지 않았다. 이 문서는 직접 읽은 코드에서 도출한 결과이며, 아래 재현 절차를 브라우저에서 실행했다고 주장하지 않는다. 실제 플레이 검증은 별도 담당 결과와 합쳐 판단해야 한다.

| ID | 중요도 | 코드로 확인한 위험 | 발생 조건 |
| --- | --- | --- | --- |
| EC-01 | 높음 | 비동기 오디오 재개가 늦게 끝나면 새로 일시정지한 게임이나 다른 게임을 재개할 수 있음 | 오디오 resume 지연 중 재정지·장면 이동 |
| EC-02 | 높음 | 잘못된 저장 데이터 타입을 받아들여 게임 완료 때 예외 발생 | completed가 true, best가 문자열 같은 손상 저장 |
| EC-03 | 높음 | 곡식 게임의 잘못된 체크포인트가 준비 실패와 재시도 실패를 반복함 | step:99 또는 sorted:null 같은 손상 저장 |
| EC-04 | 낮음 | 완료 후 삭제한 체크포인트를 주기 저장이 다시 만듦 | 곡식 게임 완료 창을 3초 이상 유지 |

## EC-01: 재개 요청 수명 검증 누락

`app.js`의 `resume()`은 창을 닫고 `paused=false`를 설정한 뒤 `await audio.resume()`을 기다린다. 기다림이 끝난 뒤 현재 전역 `game.resume()`을 호출하며, 처음 요청한 게임과 같은지, 다시 일시정지했는지, 창이 열렸는지를 확인하지 않는다.

재현 제안: CH4 일반 모드 시작 → 일시정지 → AudioContext.resume의 반환을 지연하는 테스트 장치 적용 → 계속하기 → Escape로 다시 일시정지 → 이전 Promise 해제. 일시정지 창이 열린 상태에서 게임 시간과 움직임이 재개되는지 관찰한다. 별도 사례로 대기 중 홈으로 이동한 뒤 다른 게임을 시작한다. 정상 동작은 이전 요청이 새 상태에 영향을 주지 않는 것이다. 인위적 지연을 이용한 경계 테스트이며 일반 플레이에서 빈번하다는 증거는 없다.

수정 방향: 요청 당시 게임 인스턴스와 요청 세대를 보관하고, await 이후 인스턴스·화면·일시정지·완료·모달 상태를 재검증한다. 새 정지나 장면 폐기 때 기존 재개 요청을 무효화한다.

## EC-02: 저장 맵의 타입 검증 누락

불러오기는 `parsed.completed || {}` 등의 truthy 값 검사만 한다. 따라서 `completed:true`는 홈에서 살아남을 수 있지만 ES module의 엄격 모드에서 `finish()`의 `data.completed[ch.id]=true`가 예외를 일으킨다. `best`가 문자열인 경우에도 최고 기록 대입이 실패할 수 있다.

재현 제안: 원본 저장을 백업한 격리 브라우저 컨텍스트에서 키 `joseon-memory.play.v1`에 `{"completed":true,"best":{},"snapshots":{}}`를 저장하고 다시 연다. 짧은 게임을 완료하여 결과 창과 완료 저장을 확인한다. `best:"bad"`도 별도 실행한다. 이 문제는 손상 저장을 주입한 조건이며 정상 플레이만으로 손상이 생긴다는 근거는 확인하지 못했다.

수정 방향: plain object 맵과 각 값의 타입을 검증하고 유효한 진행은 보존한다. 전체 저장을 일괄 삭제하는 복구는 피한다.

## EC-03: 곡식 체크포인트 검증 및 복구 누락

`grain.js`는 저장값을 기본 state에 그대로 합친다. `step:99`는 `[renderSorting,renderMeter,renderEvidence,renderReport][state.step]()`에서 존재하지 않는 함수를 호출한다. `step:0, sorted:null`은 진행 계산의 `state.sorted.length`에서 예외가 난다. `read`와 숫자 필드 역시 사용 전에 스키마를 검증하지 않는다.

`app.js`는 생성 실패를 잡아 다시 시작 버튼을 제공하지만, 다시 시작할 때 같은 저장 체크포인트를 전달한다. 그러므로 손상 데이터를 고치지 않으면 같은 준비 실패가 반복된다.

재현 제안: 원본 저장을 백업하고 미완료 CH6의 snapshots에 `{"6":{"step":99}}`를 주입 → 곡식 게임 시작 → 오류 창의 다시 시작을 누른다. 별도 실행으로 `{"6":{"step":0,"sorted":null}}`을 사용한다. 정상 동작은 유효한 지점 복원 또는 해당 챕터만 안전하게 새로 시작하는 것이다. 정상 체크포인트의 저장·이어하기도 함께 회귀 확인한다.

수정 방향: step 0~3, sorted의 고유한 허용 인덱스, read의 허용 키, 유한한 숫자와 범위, 단계 간 선행 조건을 검증한다. 다른 챕터의 완료·최고 기록은 보존한다.

## EC-04: 완료 후 주기 저장

3초 체크포인트 타이머는 `gameFinished`를 확인하지 않는다. 완료 처리에서 snapshot을 삭제해도 결과 창이 열린 동안 다시 저장될 수 있다. 현재 완료 챕터는 snapshot을 사용하지 않아 즉시 진행을 막지는 않지만 저장 규칙이 일관되지 않다. 완료 때 타이머를 해제하거나 완료 상태를 검사할 수 있다.

## 일시정지·키보드 검토 결과

action은 프레임 업데이트와 입력 변경에 paused/finished 검사가 있고 destroy에서 이벤트를 정리한다. rhythm은 hit와 완료에 paused/dead 검사, pause 때 프레임·음원 취소, resume 때 카운트다운 처리가 있다. grain의 주요 동작은 active 래퍼를 통한다. puzzles의 타이머는 paused/ended에서 줄지 않으며 주요 조작과 키보드 이동에 lifecycle.active 검사가 있다. 이 파일들을 직접 읽은 범위에서는 EC-01과 별개로 일시정지 중 입력이 게임을 진행시키는 확정 경로를 찾지 못했다.

브라우저 확인 필요: 각 게임에서 시간 표시와 장면을 기록한 뒤 도움/일시정지 창을 5초 이상 유지하고 방향키·Space·Enter 입력, 재개 후 상태 보존, 반복 정지/재개, 홈 이동 후 기존 타이머·이벤트 잔존 여부를 확인한다. 이 항목들은 아직 이 검토자가 실제 실행한 범위가 아니다.
